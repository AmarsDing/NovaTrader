# M03 情报处理 · 设计文档

版本 v0.3（2026-10-08）。

## 0. 评审结论（v0.2 → v0.3）

v0.2 只有流程图，以下缺口在本版补齐：

| 问题 | 处理 |
|------|------|
| 没有表结构，`news_sentiment` 只有一个 `stock_code`，放不下多标的和事件簇 | `news_sentiment` 追加字段作为条目表；新增 `intel_cluster`、`intel_link`、`stock_alias`、`intel_fact` |
| M01 的 `intel.raw.*` 没有约定载荷 | 第 2 节定义 |
| JetStream 流不含 `intel.>`，告警会丢 | `pkg/events` 加入 `intel.>`，已存在的流启动时补齐主题 |
| 近似去重、事件簇、情绪突变没有可执行口径 | 第 4、7 节给出算法与阈值 |
| M05 模型网关未建成，地址未知 | 规则打分是常驻第一层；模型打分可配置，默认关；失败标 `degraded` |
| 服务端口未分配 | 按 M00 规则：datahub 2011 → market 2021 → intel 2031/2032 |
| 时间线、热词的接口没有定义 | `api/intel/v1/intel.proto`；桌面端经 admin 聚合（M11），不直连 intel |

## 1. 流程

```
intel.raw.<kind>（JetStream）或 POST /v1/intel/items
  → 规范化 → 低质过滤 → 精确去重 → 近似去重 / 归簇      （串行，持锁，先落一条 pending）
  → 别名词典关联 → 规则分类与打分 → [小模型重评 → 重要的大模型复核]
  → 抽取公告字段 → 同一事务写评分、关联、字段、outbox
  → intel.news.scored（每簇首条） / intel.alert（命中告警条件，每簇一次）
```

服务重启时，状态为 `pending` 的条目重新走评分，保证至少一次。

## 2. 输入

主题 `intel.raw.<kind>`，`kind` ∈ `flash`（快讯）、`news`（新闻）、`announcement`（公告）、`report`（研报）、`social`（舆情）。信封用 `pkg/events`，载荷：

```json
{
  "source": "cninfo",
  "source_id": "1218765432",
  "kind": "announcement",
  "title": "贵州茅台：关于回购股份的公告",
  "content": "……",
  "url": "http://www.cninfo.com.cn/...",
  "publish_time": "2026-10-08T09:31:00+08:00",
  "codes": ["600519.SH"]
}
```

- `codes` 可选，源头自带的代码（巨潮公告、研报）。按源头信任，置信度 1.0。
- `publish_time` 缺失时用接收时间，并在条目上标记。
- 同一 `(source, source_id)` 重复到达视为精确重复。

## 3. 数据表（ent，自动迁移）

| 表 | 用途 | 关键字段 |
|----|------|----------|
| `news_sentiment` | 一条原始情报一行（已有表，追加字段） | `kind`、`source_id`、`url`、`content_hash`（唯一）、`simhash`、`cluster_id`、`event_type`、`sentiment_score`、`importance`、`half_life_minutes`、`scorer`、`degraded`、`status`、`reason`、`received_at`、`scored_at` |
| `intel_cluster` | 事件簇，近似重复的条目归一簇 | `head_news_id`、`title`、`kind`、`event_type`、`item_count`、`first_seen`、`last_seen`、`sentiment_score`、`importance`、`alerted_at` |
| `intel_link` | 条目到股票 / 概念的关联 | `news_id`、`cluster_id`、`target_type`（stock / concept）、`target`、`confidence`、`method`、`matched` |
| `stock_alias` | 人工维护的别名（曾用名、英文名、俗称） | `alias`、`stock_code`、`kind`、`confidence`、`enabled` |
| `intel_fact` | 公告抽取字段 | `news_id`、`fact_type`（amount / ratio / date）、`value`、`unit`、`text`、`start`、`end` |

`status`：`pending` → `scored`；或 `filtered`（低质）。精确重复不入库，只计数。`news_sentiment.stock_code` 保留为置信度最高的个股，兼容旧查询。

`content` 存规范化后的正文，`intel_fact.start/end` 是它的字符（rune）下标，前端据此高亮原文。

## 4. 去重与事件簇

- 规范化：去 HTML 标签与实体、全角转半角、合并空白、去首尾「来源：xx」「（责任编辑：xx）」一类尾巴。
- 精确去重：`sha256(规范化标题 + "\n" + 规范化正文)`，库上唯一约束兜底；另查 `(source, source_id)`。
- 近似去重：64 位 SimHash，特征为去掉标点后的字符二元组。48 小时窗口内汉明距离 ≤ 6 视为同一事件，归入对方的簇；文本少于 30 字时要求 ≤ 2。
  - 实测（约 90 字的公告）：加「【快讯】」前缀距离 2，追加 10 字距离 4，改一个数字距离 5；无关新闻 30 以上。经典的 ≤ 3 只适合长网页，对短新闻会漏掉大部分转载。
  - 两条都带源头代码且没有交集时不合并，防止不同公司套同一模板的公告被并成一簇。
  - 只能抓转载和小改动。不同媒体各自改写的稿件距离很远，靠 SimHash 合不起来，留给 M04 的向量检索。
- 内存保留 48 小时内的指纹，启动时从库里预热。条数到十万级前线性扫描足够。
- 每簇只有首条做模型评分、发 `intel.news.scored`、参与告警；后续条目只累加 `item_count` 和关联。

## 5. 关联

词典来源：`stock_basic`（代码、名称、去掉 `*ST`/`ST` 前缀的名称、概念）+ `stock_alias`。每 10 分钟刷新，也可经接口手动刷新。

| 命中方式 | 基础置信度 |
|----------|-----------|
| 源头自带代码 | 1.00 |
| 独立出现的 6 位已知代码（前后不是数字，后面不是「股」「元」「万」） | 0.90 |
| 全称或证券简称（≥ 3 字） | 0.90 |
| `stock_alias` 中的别名 | 按该行 `confidence` |
| 2 字简称 | 0.50（默认低于阈值，不关联） |
| 概念名（来自 `stock_basic.concept`，≥ 2 字） | 0.80 |

- 匹配用「最左最长」，不重叠，避免「平安银行」被拆出「平安」。
- 同一别名对应多只股票时，置信度除以股票数。
- 标题里出现 +0.05；同一标的多次出现，每多一次 +0.03，上限 1.0。
- 低于 `link_threshold`（默认 0.6）的不写入。

## 6. 分类与打分

规则层（常驻）按关键词判事件类型，再用极性词修正情感：

| 事件 | 例词 | 基础情感 | 基础重要度 | 半衰期 |
|------|------|---------|-----------|--------|
| earnings 业绩 | 预增、扭亏、业绩快报、净利润同比 | 由极性词定 | 3 | 5 天 |
| holding_increase 增持 | 增持 | +0.5 | 3 | 3 天 |
| holding_decrease 减持 | 减持 | -0.5 | 3 | 3 天 |
| buyback 回购 | 回购 | +0.4 | 3 | 3 天 |
| penalty 处罚 | 立案、处罚、警示函、监管函 | -0.7 | 4 | 10 天 |
| delisting_risk 退市风险 | 退市风险警示、终止上市 | -0.9 | 5 | 10 天 |
| restructuring 重组 | 重大资产重组、收购、并购 | +0.4 | 4 | 5 天 |
| contract 合同 | 中标、签订合同 | +0.3 | 2 | 2 天 |
| unlock 解禁 | 解禁 | -0.3 | 2 | 2 天 |
| suspension 停复牌 | 停牌、复牌 | 0 | 3 | 1 天 |
| policy 政策 | 国务院、证监会、央行、发改委、印发 | 由极性词定 | 3 | 2 天 |
| other 其他 | — | 由极性词定 | 1 | 按类型 |

- `other` 的半衰期按 `kind`：快讯 4 小时、新闻 12 小时、研报 3 天、舆情 2 小时、公告 1 天。
- 极性词：「增长、预增、扭亏、超预期、中标、获批」为正，「下滑、亏损、预减、违规、终止、风险」为负，按出现次数推到 ±0.6 内，与基础情感相加后截到 [-1, 1]。
- 重要度：基础值；舆情 -1；截到 0–5。常规公告（回购、增减持、业绩）停在 3，达到告警线 4 的只有处罚、重组、退市风险，以及模型上调的条目。冒烟时试过「关联个股的公告 +1」，结果每条回购公告都告警，已去掉。

模型层（`intel.llm.enabled`，默认关）：

- 小模型对每簇首条重评，输出 JSON `{event_type, sentiment, importance, reason}`；`importance ≥ review_importance`（默认 4）且配置了大模型时再复核一次，以复核结果为准。
- 走 `pkg/llm`（M05 网关）：排队优先级为批量新闻，失败熔断，每次调用写入 `llm_call_log`。地址和模型名仍在 `intel.llm`，`enabled` 默认关。
- 正文截到 2000 字，放进 `<news>` 数据块，系统提示声明忽略其中任何指令。模型没有工具，不能下单。
- 输出校验：必须是 JSON；事件类型不在枚举里按规则结果；数值截断到合法区间。任何失败都保留规则结果，`degraded = true`，`scorer = rule`。
- 没开模型时，簇首条同样标 `degraded = true`，让 M05 知道消息面只有规则分。簇内转载本来就不调模型，不标。

有效情感随时间衰减：`情感 × exp(-ln2 × 经过时间 / 半衰期)`。展示层可以把 [-1, 1] 映射成 1–10，库存只保留 [-1, 1]。

## 7. 告警

每簇最多告警一次（`intel_cluster.alerted_at`）。命中任一条件即发 `intel.alert`：

| 原因 | 条件 | 级别 |
|------|------|------|
| `importance` | 重要度 ≥ `alert_importance`（默认 4） | 5 为 critical，否则 warn |
| `sentiment_shift` | 某关联个股的综合情感变化 ≥ `alert_shift`（默认 0.5） | warn；变化 ≥ 0.8 为 critical |

个股综合情感：`E = tanh(Σ 情感ᵢ × 重要度ᵢ/5 × 衰减ᵢ × 关联置信度ᵢ)`，取近 72 小时已评分的簇首条。比较本条入库前后的 E。

告警与评分写在同一事务的 outbox 里，投递循环 500 毫秒一次。M10 订阅 `intel.alert` 决定怎么通知；M03 不直接发通知。

载荷：

```json
// intel.news.scored
{"news_id":1,"cluster_id":1,"kind":"announcement","event_type":"buyback","title":"…",
 "publish_time":"…","sentiment":0.4,"importance":4,"half_life_minutes":4320,
 "scorer":"rule","degraded":false,
 "links":[{"type":"stock","target":"600519.SH","confidence":1}]}

// intel.alert
{"news_id":1,"cluster_id":1,"reason":"importance","level":"warn","title":"…",
 "stocks":["600519.SH"],"event_type":"buyback","sentiment":0.4,"importance":4,
 "shift":{"stock":"600519.SH","before":0.1,"after":0.6}}
```

## 8. 低质过滤

- `blocked_sources` 里的来源直接过滤。
- 命中广告词（默认：加微信、免费领取、荐股、内参、开户送、扫码进群）过滤。
- 标题和正文合计少于 6 个字过滤。

被过滤的条目 `status = filtered`、`reason` 写原因，保留以便复查与去重。

## 9. 接口（`api/intel/v1/intel.proto`）

| 方法 | HTTP | 说明 |
|------|------|------|
| `Ingest` | `POST /v1/intel/items` | 手动录入，与事件入口走同一流水线 |
| `GetItem` | `GET /v1/intel/items/{id}` | 条目详情，含关联和抽取字段 |
| `Timeline` | `GET /v1/intel/stocks/{code}/timeline` | 个股时间线（按簇首条），附当前有效情感与综合情感 |
| `HotWords` | `GET /v1/intel/hotwords` | 热词，默认窗口 2 小时、前 20 |
| `UpsertAlias` | `POST /v1/intel/aliases` | 维护 `stock_alias` |
| `ReloadAliases` | `POST /v1/intel/aliases/reload` | 立即刷新词典 |

热词得分：`本窗口簇数 × log2(1 + (本窗口 + 1) / (上一窗口 + 1))`，对象为个股、概念、事件类型。

## 10. 配置

`conf.proto` 新增 `intel` 节（`Bootstrap` 字段号 33，按「30 + 模块号」分配）：`http`、`grpc`、`link_threshold`、`alert_importance`、`alert_shift`、`dedup_window`、`dedup_hamming`、`blocked_sources`、`ad_keywords`、`llm{enabled, base_url, api_key, small_model, large_model, timeout, review_importance}`。

`config.yaml` 里的时长是 protobuf Duration，只认秒，例如 `172800s`；写 `48h`、`10m` 会让所有服务启动时报错。

## 11. 代码位置

```
backend/api/intel/v1/intel.proto     接口
backend/app/intel/cmd                启动：建库、迁移、wire
backend/app/intel/internal/biz       规范化、去重、关联、打分、告警、热词、流水线
backend/app/intel/internal/data      ent 仓储、outbox、模型客户端
backend/app/intel/internal/service   proto 适配
backend/app/intel/internal/server    HTTP 2031 / gRPC 2032
backend/app/intel/internal/core      intel.raw.> 订阅、outbox 投递、词典刷新
```

M04 知识库也挂在 intel 进程里（`biz/kb`、`data/kbstore`、`service/kbsvc`、`core/kbjobs`），共用 ent 客户端和 NATS 连接。

订阅用 JetStream 持久消费者 `intel`（队列组同名，可多实例），手动确认，4 个工作协程。坏消息直接终止投递；处理出错 5 秒后重投，最多 5 次，靠库上的唯一约束保证幂等。

## 12. 不做的事

- 不做向量检索（M04）。
- 不单独建调用日志表。模型调用经 `pkg/llm` 写入 M05 的 `llm_call_log`。
- 不直接推送通知（M10）。
