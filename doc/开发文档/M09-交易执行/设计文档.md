## 1. 你安装的软件和「能自动下单」差在哪

东方财富有三层，不要混成一个：

| 软件 | 作用 | 能不能被本系统自动下单 |
|------|------|------------------------|
| 东方财富免费行情终端 | 看行情、资讯 | 不能。没有交易柜台 |
| 东方财富证券交易（需在 18.cn 开户并登录） | 人工买卖、界面里的条件单 | 条件单要人在界面里逐条设置，不适合接收我们的信号 |
| **东方财富量化终端** | 终端里「量化」入口安装，文档站 emt.18.cn / emquant.18.cn | **能。** 本地实盘方式是文件单扫单 |

量化终端里还有仿真账户，手续费可改，用来联调通道。每个账号的仿真策略数量有限（文档写每个账号最多约 10 个仿真策略）。我们自己的日常模拟盘仍在 `trade` 服务里撮合，不占用终端仿真名额。终端仿真只在联调文件单时使用。

官方还提供策略 SDK。文档写明：本地能用的实盘能力是「量化扫单（文件单）」；SDK 实盘只能在券商托管环境。所以家里的 DGX + Windows 交易机采用文件单，不采用托管 SDK。

## 2. 文件单怎么工作

终端配置：手工交易 → 文件单 → 设置输入目录、输出目录，选中账户并保持登录，开启扫单。

下单（我们写，终端读）：

1. 在扫描输入目录之外的同一文件系统中写完整 CSV，关闭并 fsync。
2. 用无覆盖的原子发布使 `<持久身份哈希>.order.csv` 一次可见，避免时间戳碰撞及部分文件。
3. 再写同名空 `.fin`，表示不再追加。**扫描器看到新增/修改 CSV 就可能处理，`.fin` 不是提交触发点或券商 ACK**。该语义已按2026-10-16官方指南修正。

撤单文件后缀是 `.cancel_order.csv`，同样加 `.fin`。

委托 CSV 表头（名称必须这样写）：

```text
sid,account_id,symbol,volume,order_type,order_business(order_biz),price,comment
```

| 字段 | 我们怎么填 |
|------|------------|
| sid | 等于 `client_order_id`，全局唯一，不复用 |
| account_id | 量化终端里的账户 ID，放配置，不进代码仓库 |
| symbol | `SHSE.600519`、`SZSE.000001`。由内部 `600519.SH` 转换 |
| volume | 股数，已按板块取整 |
| order_type | 限价单用 `1` |
| order_business(order_biz) | 买入 `1`，卖出 `2` |
| price | 限价，必填 |
| comment | 可空。不写策略机密 |

股票限价、买、卖的取值来自官方数据字典（order_type=1 限价；股票 order_biz 1 买入、2 卖出）。上线前用仿真账户对一笔，确认终端版本没有改字典。

终端写回（我们读，按账户 ID 分子目录）：

| 文件 | 刷新方式 | 用途 |
|------|----------|------|
| cash.csv | 整文件覆盖 | 资金、可用 |
| position.csv | 整文件覆盖 | 持仓、今日仓、可卖 `available_now` |
| order_status.csv | 整文件覆盖 | 委托状态、已成数量、柜台 `order_id` |
| execution_report.csv | 末尾追加 | 成交回报 |
| order_status_change.csv | 末尾追加 | 状态变化流水 |

`position.csv` 的 `volume_today` 是今仓，`available_now` 是当前可卖。对账时以这两个字段校正本地 T+1 账本，不一致就告警。

## 3. 进程怎么接

```
DGX：trade
  风控通过后的订单
      │  HTTPS JSON（局域网 mTLS；proto-first合同）
      ▼
Windows：broker-gw
  只在本机写 CSV / 读 CSV
      ▼
东方财富量化终端（已登录）
      ▼
东方财富证券柜台
```

DGX 与 Windows 不共享磁盘。`trade` 不能直接写 CSV，必须由本机 `broker-gw` 写。`broker-gw` 不保存交易密码，不落订单库；订单真值在 `trade` 的 PostgreSQL，柜台真值以扫单输出为准。

终端进程退出、扫单关闭、输出文件超过 N 秒不更新：`broker-gw` 报不健康。有实盘持仓时，`trade` 停止新开仓并通知你。已经发出、尚未确认的订单标成 `UNKNOWN`，只通过对账查 `sid`，不自动再写一张单。

## 4. 订单状态

```
CREATED → 风控拒绝（结束）
       → APPROVED → 半自动则等待你在客户端确认（超时作废）
                  → 提交中 → 已报 → 部分成交 → 全部成交
                           → 撤单中 → 已撤
                           → 柜台拒绝
                           → UNKNOWN（等对账，不重发）
```

模拟盘不写文件，走内存撮合器，状态机相同。

盯盘卖出（`source=watch`，来自可信内部 `risk.exit` 消费者）仅在账户/持仓匹配、保护规则有效预授权、当前未停止且最终风控通过时不等实盘确认窗；客户端自报watch不是授权，无有效授权则转人工处理或明确阻塞。仍挂着的限价单超过60秒可按政策撤剩余，LIVE必须收到真实撤单确认后才允许重报；按0.01元向不利方向重报最多2次，卖出不低于第一张单99.5%、买入不高于100.5%。到次数/价格边界只撤单并写原因。手动单和普通自动单不追价；重报ID为原ID加`#1`、`#2`，状态与真实回报关联。

## 5. 和条件单的分工

量化终端自带条件单、网格、涨停开板。那些是在终端界面里人工配置的。本系统的止损、止盈、时间止损由 M08 盯盘，触发后仍生成一张普通限价文件单。不在终端里再挂一套条件，避免两边同时卖出。

## 6. 回写信号

成交和下单状态由本模块维护，信号状态仍只经 M06 的 `Transition` 修改。

- 买入委托有成交：把对应买入信号迁到 `done`，操作方 `trade`。
- 这只票的仓位归零：把**同一条买入信号**从 `done` 迁到 `closed`，带上 `exit_price` 和 `pnl_pct`。`pnl_pct` 是百分比，3.2 表示赚 3.2%，按实际成交价计算，不是按信号里的计划价。
- 卖出信号在卖出成交后停在 `done`，不要迁到 `closed`。仓位还没卖完也不要迁，M06 会因此停止按原止损止盈检查。

M04 只在 `closed` / `expired` / `cancelled` 时建案例，所以平仓必须走这一步，不能只发 `trade.fill`。

## 7. 上线顺序

1. `trade` + 模拟撮合（不需要东财账户）。
2. 你开通东方财富证券，并在量化终端登录，配好扫单目录。
3. 仿真账户：买入、撤单、卖出各一笔，对上 `order_status.csv`。
4. 模拟盘连续满20个交易日，运行证据与准入清单通过，真实文件单/回报/对账联调完成。
5. 开放账户与预算严格受限的L2，人工确认小额实盘验收；验收前不扩大额度，不在L1先绕过授权做实盘。

## 9. N0-01账户合同与日初结转（2026-10-15）

共享`pkg/accountstate.Snapshot`定义版本化完整快照，字段及数据流见[实施记录](../实施记录/N0-01-账户合同-2026-10-15.md)。`Snapshot`从实际现金、持仓与全量订单组装：现金扣在途买单剩余金额和费用后得到可用，卖单剩余数量占用可卖，pending/partial/UNKNOWN等不释放占用。各SIM/LIVE仅支持`default`账户，未接入的LIVE不初始化虚构资金，对账为unavailable。

`CommitSnapshot`同事务保存完整JSON state、日初资金行及outbox；generation取快照持久行ID。旧摘要列和历史记录保留，但不供risk恢复完整账户。原订单/成交/资金/持仓Commit事务仍保留；快照读取以单Engine写锁串行，跨实例原子claim和持久执行意图依赖N7，不作已有保证。

新SIM账本基线是实际配置初始资金，旧账本缺基线保持未知。交易日第一次下单/撮合/快照先按旧账面市值锁定日初并结转旧股；随后当日买入不进入可卖。相同日RollDay幂等，非交易日不结转，账期未锁定却已有当日成交则停止推定结转。自动结转不增加旧paper_days；连续日准入另取N7运行证据。

`Reconcile`的差异事件改发`trade.reconciliation`，不再发部分`trade.account`；比较数量与可卖差异，既有停止开仓不自动解除。成功完整快照才发送`trade.account`。风险启动恢复与订阅遵循M08新合同。当前无真实柜台对账，不把本地matched标为实盘一致。

## 10. N8-01/02 隔离网关（2026-10-17）

实现与验收边界见[隔离文件单网关记录](../实施记录/N8-01-02-隔离文件单网关-2026-10-17.md)及仓库 `broker-gw/README.md`、`protocol-manifest.json`。独立Python标准库进程、原子文件发布、持久运输占用、覆盖/追加回报读取、撤单/部分与晚成交查询、资金/持仓/委托/成交量金额对账、mTLS接口和Go `pkg/brokerif/remote` 调用口已交付。

运输spool只防止重发，不是第二业务订单库。同sid同内容重试返回原结果，差异冲突；占用后崩溃/权限/磁盘错误保持UNKNOWN，不能重新分配身份。`.fin`、FILE_PUBLISHED、撤单文件发布均不能代替柜台回报。回报用账户/sid/exec_id和语义版本去重，recv_at改变不是新成交。读完整前缀上限8MiB/10万行，超过限制明确阻塞，长期轮换与消费游标待接trade。

TLS显式启动、CA及客户端证书指纹双校验，固定账户及协议，Go校验CA/SAN并禁止重定向。当前只有ISOLATED根目录，无LIVE开关；返回的文件新鲜度不是终端登录/扫描心跳。`terminal_login_verified`、`cross_file_atomic`、`can_open_live`均false。生产trade未接通该出口，不能因为调用口可编译就置BrokerConnected或放开L2。

后续部署须用真实终端导出确认字段/编码/枚举，完成跨主机证书、故障、启动和持续对账，再将回报幂等写入trade PG/outbox。恢复开仓需完整账户/数据/授权/风险/准入检查；对账结果本身不自动解除停止状态。
