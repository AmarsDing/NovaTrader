# 监控与盯盘业务深化方案

> 2026-10-15：后续实施顺序统一到[总体方案N0–N9](量化智脑与自动交易总体实施方案.md)与[AI任务书](AI分阶段实施任务书.md)。本文D0–D5保留详细业务合同和已做记录，映射见新方案§14；更强玻璃/霓虹按视觉规范第七节，原画布与票式布局继续采用。

日期：2026-10-14（Asia/Shanghai）  
状态：用户已确认产品方向；第一批基础修正、连线检视与白话行动层已实现。本文件同时包含后续合同，未完成项以第9节的进度为准。

## 1. 设计基线

沿用原有设计，大方向不变：

- **监控**：独立 /monitor，保留 ComfyUI 式可拖拽纤维画布、三段业务拓扑、时段带、HUD、底部终端带、原详情窗与科技视觉。
- **盯盘**：保留 dockview 工作台、居中的决策台、右侧涨停/行情/信号/情报标签组、下方交易，以及“一张票”的阅读方式。
- **深化位置**：监控加深节点、连线、数据样本、处理追踪与配置；盯盘加深汇总结论、条件计划、持仓处置与执行结果。主画面结构继续稳定。
- **技术**：Tauri + Vue、Go/Kratos、PostgreSQL/ent、NATS/Redis 保持既有架构。

原呈现合同见《监控驾驶舱呈现方案》§0.5–0.6；工作台合同见《个人交易信息全览方案》§6 和 M12 设计§12。本文件补充业务含义、深度交互与执行闭环。市场参考和上一轮概念稿仅作局部借鉴，后续实施以原设计和本文件为准。

## 2. 两块面板围绕同一条业务链

```text
数据源 → 标准化/质量校验 → 市场/情报处理 → 四维研判
      → 规则与模型融合 → 规则计算交易计划
      → 当前账户与授权校验 → 风控 → 委托
      → 终端回报 → 成交/持仓 → 对账与后验
```

**监控看这条链如何工作、在哪里失效、如何配置；盯盘看这条链得出的当前结论、行动条件与执行结果。**

两页共享证券、交易日、账本、信号、研判、计划、策略版本、配置版本、订单与 trace 标识。点击一条结论进入监控时，直接突出产生它的实际路径；从监控进入盯盘时，带回同一张票，避免用户重新搜索。

展示、人工确认和自动执行消费同一份后端计划。浏览器负责呈现与交互，不能自行算出另一份可交易结论；大模型继续只提供评分、理由与证据，价格、仓位、触发和执行由规则与风控决定。

## 3. 监控面板：在一页内检查并配置整个业务

### 3.1 主画面继续回答六个问题

1. 系统当前能提供哪些业务，哪些不可用？
2. 数据进来了吗，源头数据是不是新鲜、完整？
3. 哪个扫描/专家/模型正在工作，输出了什么？
4. 哪些信号正等待条件、人工确认或风控？
5. 哪些订单已提交、部分成交、结果待核对？
6. 哪处异常影响了哪些证券、计划或账户？

HUD 展示业务摘要和最重要阻断项，画布保留稳定拓扑。健康总分旁显示已观测覆盖；无法测量不能被高分掩盖。底部继续承载事件、日志、任务/准入、模型与账本，详细字段按选择对象联动。

### 3.2 节点详情统一深化

沿用原详情窗，可固定并展开宽度；保留画布和已选路径。所有节点使用共同的六类内容，不要求没有能力的节点显示空页签：

| 内容 | 用户能看到什么 |
| --- | --- |
| 概况 | 这一步做什么、当前状态、最近成功/失败、影响范围、下一检查项 |
| 输入 | 实际使用的行情、因子、新闻、账户等样本；数据源、证券、时间、单位与质量 |
| 输出 | 本次标准化数据、筛选结果、四维评分、规则计划或订单；前后数量与变化 |
| 质量 | 缺失、陈旧、重复、异常、隔离、降级；检查规则、阈值、原始证据 |
| 记录 | 最近处理任务、耗时、错误、重试、相关事件；从当前对象进入一次完整追踪 |
| 配置 | 当前值、可编辑草稿、参数解释、前后差异、版本、生效服务和验证结果 |

不同节点进一步显示其业务内容：

| 节点 | 需要深化的业务信息 |
| --- | --- |
| 数据源 | 实际上游与数据域、当前主备、支持市场/频率、请求数与数据条数、延迟、覆盖率、源时间、切源原因、原始与标准化样本 |
| 扫描 | 本轮证券池、每层输入/通过/过滤、具体过滤原因、候选与漏选、所用模板和版本 |
| 技术/消息/资金/外围 | 本次输入事实、各维结论、支持与反对证据、缺失维度、关联来源与数据时间 |
| 模型 | 模型/档位/版本、事实包摘要、结构化输出、耗时/队列/用量、失败/降级、负责哪些任务 |
| 综合与信号 | 各维与规则的贡献、异议、融合方式、计划触发条件、有效期、未行动原因 |
| 风控 | 当前授权、已检查规则、拒绝/缩量原因、账户预算与占用、保护性退出和急停状态 |
| 账户与交易 | 权益/现金/总量/可卖/冻结、在途委托、真实回报、对账差异、计划与成交的关联 |
| 数据库/消息总线/GPU | 连接、队列/积压、资源、故障，以及实际受影响的业务；不能只显示硬件百分比 |

模型详情展示已记录的输入事实、输出结论、证据和运行信息；不要求生成或展示模型内部思维过程。缺失字段明确写明缺口。

### 3.3 连线成为可检查的业务通道

单击连线打开同一详情窗，展示生产者、消费者、数据类型、最近样本、窗口内请求/记录/字节数、处理耗时、错误、积压和最近消费确认。高亮关联节点，可分别进入上下游。

每条边固定注明：**观测来源、计量单位、统计窗口、覆盖范围**。原有环境流向点继续只表示结构方向；真实脉冲、失败和吞吐变化对应实际事件。

当前源 successCount 是请求成功数，模型 calls 是档位调用数，不能直接当每条边的数据条数。没有逐边计量时显示“来源请求速率参考”或“未观测”，不能给未知管道填 0。

结构关系和本次实际经过的路径分别表达。上游与某专家存在配置依赖，不代表这条信号真的使用了该源。

### 3.4 从一条数据追到一笔订单

按证券、信号、订单或 trace 检索；画布突出本次处理走过的节点，底部事件带切为对应时间线。每一步显示：

“输入了什么 → 使用什么规则/版本 → 产生什么输出 → 花多久 → 下一步是谁 → 是否成功”。

保留 source event、decision、signal、plan、order、fill 的显式关联。一次扫描可能让多只证券共用trace，查看单只证券时同时按证券和业务对象约束；不能将同trace的全部步骤视为该股路径。缺少关联显示“该步未观测/尚未关联”，不能仅凭时间接近就断言存在因果关系。

时间分别保留：数据实际发生时间、系统接收时间、服务处理起止、页面采样时间。行情时间不能被接收或展示时间覆盖。

### 3.5 配置在监控详情中完成

配置范围按阶段接入：数据源与优先级、模型与四维分工、扫描与策略、风控限额、通知、自动计划的账户/策略/证券范围与预算。复杂参数在详情里编辑，主画面仍只显示状态和摘要。

配置过程固定为：

```text
查看当前值 → 编辑草稿 → 校验与影响预览
          → 保存版本 → 等待服务加载 → 核验生效
```

| 项目 | 设计要求 |
| --- | --- |
| 说明 | 白话解释参数控制什么；同时提供专业名称、单位、范围和默认值 |
| 预览 | 显示变更项及受影响的账户、策略、数据域、任务或节点；权重同时显示归一化后的实际比例；未经模拟不预测交易笔数与收益 |
| 生效 | 分开显示保存版本与各服务实际加载版本；未有回执就显示“已保存，生效待验证”；加载失败保留该服务上个有效版本，多服务未对齐显示“部分应用”并阻塞依赖这些版本的新计划，不能宣称全系统生效 |
| 并发 | 保存带基础版本；版本已变要求重新比较，避免覆盖别人或另一页的修改 |
| 历史 | 查看操作者、前后值、版本和结果；恢复历史配置先形成新草稿并沿用相同校验 |
| 权限 | viewer 只读；owner 的写入仍由后端校验；敏感值仅显示是否配置，留空/替换/清除含义明确 |
| 交易相关 | 修改预算或策略参数不等于启用自动执行；原计划、持仓保护和新计划的适用版本分别展示 |

监控可配置自动执行政策并查看运行状态；启用执行、确认订单及急停继续从原交易工作台完成。配置保存不产生订单，也不自动恢复已停止的交易。

统一的是配置入口和交互，不是一个无差别保存接口。数据源/模型等现有白名单项复用GET/PUT /api/config；风控限额保留风险专用校验与写契约，自动执行政策采用账户权限、版本和审计的专用契约。不能把敏感交易政策直接加入通用配置白名单而绕开原服务检查。

### 3.6 异常与历史

异常入口直接定位到第一处已观测异常，显示受影响证券、计划、订单，以及仍可继续的能力。提供“查看依据、相关日志、恢复验证”的短路径。

后续增加统一时间范围：实时、最近15分钟、今日、指定交易日。画布、HUD、详情和事件共同切换；历史模式持续显示“历史查看”，配置/执行入口不可混用历史上下文。当前会话曲线与短期脉冲不等于服务端历史归档，完整回放需要持久化补充。

时间合同区分窗口统计from/to与选中时点at；历史查询冻结上下文，不能混入at之后的事件或未来才可获得的结果。历史浏览时，当前实盘异常与急停提醒仍独立出现并标“实时”，不覆盖正在查看的历史画布。

## 4. 盯盘面板：先给结论，再解释依据

### 4.1 保留布局，深化三个阅读层次

| 层次 | 放在哪里 | 回答什么 |
| --- | --- | --- |
| 汇总判断 | 原决策台顶部摘要区 | 现在能做什么，先处理谁，账户还能承担多少 |
| 当前行动 | 原“一张票”正文最前 | 这只股票现在该等、买、持有、减仓还是退出；条件是什么 |
| 专业依据 | 原价格、四维、异议、理由、风控及右侧专业标签 | 为什么这样判断，证据是否可靠，具体规则与数据是什么 |

简明与专业是同一份结论的不同深度，不维护两套模型结论。白话优先使用确定的结构化字段和文案模板；证据不足明确说不足。

结论优先遵从数据有效性、当前授权、账户约束和风控阻断，再表达策略方向；高评分不能覆盖关键阻断。必要/可选数据由策略版本声明，可选维度缺失时如实标降级，不能随意把它当作规则反对票或零分。

### 4.2 汇总后的专业数据看板

沿用顶部现有区域，增加业务结论和窗口说明：

| 汇总内容 | 面向不懂股票规则的表达 |
| --- | --- |
| 当前行动政策 | 可评估新开仓 / 谨慎参与 / 仅处理持仓 / 暂停新开仓 / 数据不足暂不能判断 |
| 先处理事项 | 哪些持仓触发退出、哪些委托待核对、哪些计划即将过期 |
| 可行动候选 | 满足计划条件、等待条件、被阻断分别多少；不是所有高分信号数量 |
| 账户预算 | 可用资金、仓位占用、允许新增预算、哪项限额限制；注明是否只为估算 |
| 市场结构 | 情绪、上涨/下跌、封板/炸板、主线与广度；每个结论附最主要依据和观察窗口 |
| 数据可信度 | 行情、账户、消息、模型分别是否有效及截至时间；关键缺口覆盖当前行动判断 |
| 策略表现 | 已完成样本的费用后结果、样本数、区间、版本；不能把评分叫获胜概率 |

汇总行动政策来自配置的规则和风险状态，不让模型自由编一个“适合买入指数”。核心数据缺失显示“无法判断”，与规则已评估后“没有合格计划”区分。

原左栏待执行/已执行/漏选保留。待执行内部按保护性退出、待核查订单、即将失效计划、有效买入排序；一票明确“待评估/等条件/待确认/已提交”，不能把这些统称为可以下单。

### 4.3 每张票先显示一份白话行动计划

固定回答七件事：

1. **现在做什么**：等待、满足买入条件、继续持有、建议减仓、触发退出、当前不可执行。
2. **什么时候做**：哪些价格/量能/时间/规则条件满足后行动，最晚有效到何时。
3. **做多少**：规则建议股数、估算金额和仓位；风控预检后允许值与建议值分开。
4. **为什么**：两三条关键理由，最重要反证或风险直接可见。
5. **什么会让计划失效**：超出入场范围、信号过期、条件改变、必要数据陈旧等。
6. **怎样退出**：保护规则、目标退出、最长持有及可卖限制。
7. **谁在执行、执行到哪**：未启用、等待人工、模拟自动、委托中、部成、成交、待对账。

策略评分只叫评分。计划止损损失是按价格和数量的估算，标注费用与滑点口径；止损触发不代表能够按该价成交。

“何时买卖”使用可观测的条件和有效窗口表达。只有已有时间规则才给时间点；不编造未来必然上涨、下跌或精确成交时刻。

### 4.4 候选、持仓、委托各自有直接结论

| 对象 | 结论重点 | 必须展示的限制 |
| --- | --- | --- |
| 未持仓候选 | 等什么条件、什么区间允许买、超价是否放弃 | 有效期、关键数据、账户授权、规则预算 |
| 已持仓 | 继续持有、触发保护/目标/到期退出、是否需减仓 | 总量/可卖/冻结、在途卖单、所属计划、最新保护规则 |
| 已委托 | 已报、待回报、部分成交、撤单中、结果待核对 | 成交量、剩余量、最后回报时间；委托不是成交 |
| 已完成 | 实际如何完成，与原计划差在哪里 | 真实费用后结果、退出原因、策略/参数版本 |

可卖为0时，使用白话说明原因，例如“这部分持仓当前不能卖出”；有可靠交易日历和规则依据时才显示下一可评估时点。触发退出但不可卖不能显示“已经止损”。

**虚构示例，仅演示文案：**

> 当前：等待，不追价。  
> 计划只在10.00–10.10元且量能条件满足时考虑买入；当前10.18元，不在区间内。有效到10:30。  
> 若达到条件，系统重新检查行情、账户与风险，再按当前授权方式处理。

> 当前：保护性退出条件已触发。  
> 当前可卖200股，关联卖单已提交，等待成交回报；剩余持仓仍继续显示风险。  
> 若可卖为0，改为“当前不可执行”并显示原因，不反复提交失败卖单。

### 4.5 日常操作保持简洁

每种状态只给一个主要动作：等待时“关注条件”，可提交时“查看并确认计划”，持仓时“查看退出计划”，结果不明时“核对委托”。查看依据、查看行情、进入监控为次要动作。

确认页预填证券、方向、价格、股数及依据，携带信号/计划/策略版本；用户不需要重复输入。执行前后端重新检查有效期、行情、账户、授权、在途和风控，旧预览不能代替最终校验。

预览必须无交易副作用：不能为了刷新卡片而反复调用会占用限额、计数或预留的正式 CheckOrder。若尚无纯预检接口，显示“规则估算，提交前检查”，不能称“风控已通过”。

### 4.6 白话与专业术语对应

每个关键术语第一次出现给一句话解释，详情保留原字段、公式、单位、窗口与来源。例如“量比”说明为“相对基准的交易活跃程度”，“仓位”说明为“这笔持仓占账户权益多少”，“可卖数量”说明为“当前实际允许卖出的股数”。不同来源口径不能只因中文名相同而合并。

事实、规则判断、模型意见与待验证项有明确标签；日常主票最多突出一个当前动作和两三条关键理由，其他字段展开查看。按钮文案写具体动作，用户无需记住Rxx、F:、N:等内部编号才能操作。

## 5. 同一份交易计划支撑展示与自动化

先扩展现有信号/策略版本承载条件计划与读模型；需要独立持久化生命周期时再增加 ent schema，不复制账户、订单或成交账本。

建议计划至少具备：

| 字段组 | 内容 |
| --- | --- |
| 身份 | plan_id/revision、signal_id、decision_id/trace_id、证券、book + account_id、策略与规则版本；LIVE另核对可信broker账户绑定 |
| 事实 | input_snapshot_id、各必要数据的源时间、质量/降级状态、证据引用 |
| 行动 | 候选或持仓、方向、条件表达式、入场区间、时间窗口/有效期、数量与预算 |
| 退出 | 止损/目标/到期等规则、优先级、可卖限制、已有在途订单；绑定position_generation_id或明确开仓成交关联，避免旧事件作用于同证券的新一轮持仓 |
| 可执行性 | 条件结果、阻断原因、预检时间/版本、是否待确认；与交易所成交状态分离 |
| 生命周期 | 等待/触发/失效/执行中/完成/停止；触发周期、已消费标记、关联订单 |
| 授权 | 当前执行政策、账户/策略/证券/时段/资金范围、授权版本和操作者 |

价格与数量由规则计算，正式风险检查可以拒绝或缩量。计划变更形成新版本，旧版不能继续被新事件执行；已成交持仓的保护不能因新版计划而无声移除，规则迁移必须有明确结果。计划、预算、授权、订单与回报核对同一个account_id，界面切换当前账户不能重定向已有计划；当前可先约束每个账本唯一固定账户，未来多账户需要显式扩展契约。

## 6. 自动化交易分阶段贯通

### 6.1 用户能理解的控制面

| 维度 | 表达 |
| --- | --- |
| 账户身份 | SIM 模拟 / LIVE 实盘，附账户别名 |
| 运行授权 | L0 观察 / L1 模拟 / L2 实盘人工确认；L3 当前未开放 |
| 市场/账户风险状态 | 正常、谨慎、停止新开仓等；不是 L0–L3 的另一种叫法 |
| 自动计划状态 | 未启用、运行、暂停开仓、阻塞、停止中、已停止 |

账户与运行授权分别保存、分别显示，合法组合由后端判断。查看 LIVE 账户不等于授权实盘执行；保存自动化参数不等于启动交易。

### 6.2 路径与准入

| 阶段 | 行为 | 验收重点 |
| --- | --- | --- |
| A 智能建议 | 汇总信息、形成条件计划、白话解释与证据下钻 | 口径/数据时间/有效期准确，未知与不交易区分 |
| B 模拟确认 | 同一计划人工确认后在 SIM 执行 | 风控、委托、成交、持仓、后验完整关联 |
| C 模拟自动 | SIM 内自动监测、消费获授权计划 | 幂等、异常演练、连续交易日证据、恢复与对账 |
| D 半自动实盘 | LIVE 在限额内人工确认开仓；保护性退出按明确的预授权政策处理 | 连续满20个交易日且准入通过；真实文件单、回报与对账完成 |
| E 未来全自动 | LIVE 在获准账户、策略、时段与预算内自动执行 | 独立准入与执行政策；当前 L3 保留不能直接视为已开放 |

连续20个交易日是半自动实盘准入的一部分，不是全自动开关。记录应按交易日幂等，能证明实际连续运行、异常处理与验收结果；不能靠重复调用累加天数。

自动执行链固定为：合法计划版本 → 条件触发 → 确定稳定client_order_id并持久化执行意图 → 执行授权 → 带该ID正式风控/预留 → 委托 → 真实回报 → 成交/持仓 → 计划/信号状态 → 对账。

同一执行意图重试复用原ID；消费记录区分处理中、已提交、终结，不能在授权或临时风控失败前就永久标为已消费。持久化意图、订单关联及状态迁移需保持一致，崩溃恢复先查原订单结果。保护性退出免确认仅适用于可信内部来源、匹配账户/持仓、有效预授权且当前状态与最终风控允许的情形，不能凭客户端自报source=watch绕过确认。

### 6.3 停止与异常的业务语义

| 情况 | 系统与界面要求 |
| --- | --- |
| 暂停开仓 | 停新开仓并按政策处理在途买单；原授权保护退出是否继续明确显示 |
| 停止自动 | 停新自动触发，处理在途；显示“停止中：待确认撤单N笔”，收到回报后才能称已停止 |
| Kill Switch | 现有策略降至L0，自动退出也停止，人工卖出仍需风控；页面明确提示待人工处理，不能称保护仍在执行 |
| 部成与撤单竞争 | 以真实回报更新已成/剩余；未确认已撤前不对同一剩余量盲目重报 |
| 失联/UNKNOWN | 停新开仓，查原订单回报；不换新ID重发结果不明的委托 |
| 可卖不足 | 按账户可卖与冻结重新计算，等待状态变化，不循环提交同一错误单 |
| 重启恢复 | 先恢复停止/授权状态，读取旧单/回报/冻结并对账，再决定是否恢复运行 |
| 旧信号/重复事件 | 检查账户、持仓代次、交易日、有效期、计划版本与执行意图状态；不再次执行过期或已完成意图，不让旧退出作用于新一轮持仓 |

数据库唯一约束、条件状态迁移、回报幂等和可恢复的持仓预留构成执行保证。内存 mutex 或 NATS 去重不能单独证明跨进程不会重复下单。

## 9. 实施顺序与验收场景

| 批次 | 内容 | 交付结果 |
| --- | --- | --- |
| D0 | 修数据口径、时间、事件、账户身份、交易刷新与关联 | 屏幕状态与真实业务一致 |
| D1 | 原监控详情深化、原票式决策增加白话行动与持仓计划 | 同一页能看详情、看依据，明确下一步 |
| D2 | 样本/边/追踪/配置预览与生效核验 | 从一条信号追到实际数据与订单；修改配置能核验加载 |
| D3 | SIM计划编排、幂等、停止、恢复、对账与后验 | 同一份计划完成自动模拟闭环 |
| D4 | 交易日证据、真实文件单/回报、半自动准入 | 条件满足后分阶段开放半自动实盘 |
| D5 | 独立全自动准入、历史回放与更完整逐边计量 | 后续阶段；本次未开启或承诺已完成 |

验收至少覆盖：

1. 点击源节点能看到一条原始数据、标准化结果、单位和三个时间；点击边能说明计量依据。
2. 从一条信号追到四维证据、规则/配置版本、计划、委托与成交；缺步骤明确标缺口。
3. 保存配置后区分已保存与各服务已应用；冲突、加载失败与恢复都有确定结果。
4. 不懂指标的用户可在主票直接读懂当前动作、等待条件、可卖限制和主要风险；专业用户能展开到原始字段。
5. 高分但过期、行情陈旧、风控拒绝、仅在候选池中的信号不能表现为可买。
6. 委托部成、撤单竞争、UNKNOWN、重启、重复事件不会变成重复成交意图；计划与账本可以对账。
7. 暂停与急停语义清楚，实际停止状态来自后端和回报，不由按钮点击直接宣告完成。
8. 保持原画布、票式决策与工作台布局；只改变业务深度和局部交互，窄屏不靠缩小关键文字解决。
