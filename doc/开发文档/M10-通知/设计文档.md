# M10 通知 · 设计文档

| 项 | 内容 |
|----|------|
| 版本 | v0.3（2026-10-09 评审后补齐服务、事件、分级、免打扰、合并、模板、落库） |
| 服务 | `notify`，代码 `backend/app/notify`。HTTP 2101、gRPC 2102（M00 第 5 节 20x1 规则，M10 取 10） |
| 配置 | `conf.Bootstrap.notify`，字段号 40（30 + 模块号） |

需求原文不改。下面这些是 v0.2 没写死、不对齐就无法实现的部分。

## 1. 流程

```
JetStream 事件
  → 按 event_id 幂等落库
  → 同一 dedup_key 在合并窗口内并入先到的那条
  → 免打扰：非放行时段只放行 critical，其余标 held
  → 渲染模板
  → 桌面、飞书各自重试
  → 回写渠道状态
```

飞书只有出站 Webhook，没有回调，消息里没有按钮。实盘确认只在桌面客户端做，本服务不提供确认接口。

桌面通道：本服务把 `notify.desktop` 发到 JetStream，admin 订阅后用现有 WebSocket 广播 `e=notify`。客户端只连 admin 的 2003，不直连本服务。

## 2. 优先级

| 优先级 | 来源 | 说明 |
|--------|------|------|
| critical | `strategy.signal.updated` 且 `status=pending` | 新交易信号。之后的状态变化不通知，成交走 `trade.fill` |
| critical | `risk.alert` | 熔断、Kill Switch、拒单率 |
| critical | `intel.alert` 且 `level=critical` | 突发利空 |
| critical | `notify.request` 的 `level` 不是 `info` | 数据源切换、快照不可用、数据不是最新。`info`（例如源恢复）降为 medium |
| high | `strategy.briefing` | 晨报 |
| high | `trade.fill` | 成交。数量为 0 的忽略 |
| high | `intel.alert` 且 `level` 不是 critical | 普通情报告警 |
| medium | `strategy.review` | 复盘。M05 尚未发布该主题，本服务先按这个载荷订阅 |
| medium | `notify.request` 且 `category=review` 或 `level=info` | 没有专用主题时的入口 |

`notify.request` 若自带 `category`（`signal` / `risk` / `briefing` / `fill` / `intel` / `review`），按上表，不再看 level。

## 3. 免打扰

放行时段（交易日）：`PRE_OPEN`、`CALL_AUCTION`、`PRE_MATCH`、`AM_TRADING`、`PM_TRADING`。时段用 `pkg/tradecal`，不自己比钟点。

免打扰：`NOON_BREAK`、`POST_CLOSE`、`CLOSED`，以及非交易日全天。

critical 任何时段都发。high 和 medium 在免打扰时段写成 `held`，进入下一个放行时段再发。晨报在 08:30 生成，当时是 `PRE_OPEN`，所以会立刻发出，不会被压到 09:30。复盘若在 15:00 之后生成，优先级是 medium，记下来，下一交易日 07:30 再发。

日历判断失败时，非 critical 先压住。

## 4. 订阅

持久消费者，手动确认。处理成功（含渠道失败但已落库）才 Ack。数据库不可用时 Nak，等 JetStream 重投。同一 `event_id` 再来直接 Ack。

首次创建消费者用 `DeliverNew`，避免把流里旧消息补发成通知。进程重启后从上次确认的位置继续。

| 主题 | 消费者 | dedup_key |
|------|--------|-----------|
| `notify.request` | `notify-request` | 载荷里的 `dedup_key`，没有则 `category:title` |
| `strategy.signal.updated` | `notify-signal` | `signal:{signal_id}` |
| `risk.alert` | `notify-risk` | `risk:{kind}:{account_type}` |
| `intel.alert` | `notify-intel` | `intel:{cluster_id}` |
| `trade.fill` | `notify-fill` | `fill:{订单号}:{代码}:{方向}:{数量}:{价格}` |
| `strategy.briefing` | `notify-briefing` | `briefing:{date}` |
| `strategy.review` | `notify-review` | `review:{date}` |
| `sys.session.changed` | `notify-session` | 不产生通知，用来立刻补发 held |

成交载荷目前是 Go 结构体的默认字段名（`Symbol`、`Qty`）。解析时两种写法都认。

`strategy.review` 载荷：`date`、`title`、`body`。`title` 空则用「复盘 {date}」。

## 5. 合并

窗口默认 60 秒，配置 `merge_window_sec`。同一 `dedup_key` 已有一条 `sent` / `partial` / `held` / `pending` 时，新到的标 `merged`，并入那条，`merge_count` 加一。已经发出的正文不改、不重发。还没发出的（held）改成最新的标题和正文，补发时带上条数。

进入放行时段补发时，同一 `dedup_key` 的 held 再收成一条，只发最新的正文。

## 6. 模板

配置 `templates` 按 category 覆盖。缺省是 `{{title}}\n{{body}}`。可用 `{{title}}` `{{body}}` `{{category}}` `{{priority}}` `{{count}}`，以及该条事件带上的 `symbol`、`side`、`qty`、`price`、`date`、`kind`。`{{count}}` 是这条加上被合并的条数。

改模板要重启进程。飞书机器人若要求关键词，把词写进对应模板。

## 7. 渠道

两条渠道互不影响，并行发送。每条最多 `retry_max` 次（默认 3），间隔 1 秒、2 秒、4 秒。

| 结果 | 条件 |
|------|------|
| `sent` | 至少一条渠道成功，另一条成功或跳过 |
| `partial` | 一条成功，另一条失败 |
| `failed` | 没有一条成功 |
| `skipped` | 飞书 Webhook 为空。这不是失败 |

飞书 POST JSON：`msg_type=text`，`content.text` 为渲染结果。配置了 `feishu_secret` 时附带官方签名。不使用交互卡片。

桌面载荷只有 `id`、`event_id`、`priority`、`category`、`title`、`body`、`at`。没有确认动作。

admin 转发失败不影响落库。admin 连不上 NATS 时只记日志，HTTP 和 WebSocket 照常启动。

## 8. 表 `notify_message`

一条上游事件一行。

| 列 | 说明 |
|----|------|
| `event_id` | 唯一，幂等 |
| `trace_id`、`source`、`subject` | 信封 |
| `category`、`priority`、`title`、`body` | 渲染前的内容 |
| `fields` | 模板变量 |
| `dedup_key`、`merge_count`、`merged_into` | 合并 |
| `status` | `pending` / `sent` / `partial` / `failed` / `held` / `merged` |
| `rendered` | 实际发出的正文 |
| `desktop_status`、`desktop_attempts`、`desktop_error` | 桌面渠道 |
| `feishu_status`、`feishu_attempts`、`feishu_error` | 飞书渠道 |
| `created_at`、`sent_at` | 时间 |

启动时把残留的 `pending` 再看一遍：当时如果处于免打扰且不是 critical，改成 `held`，否则再投递。

## 9. 接口

`api/notify/v1/notify.proto`。客户端不直连，查询以后由 admin 转发（M11）。

| 方法 | HTTP | 说明 |
|------|------|------|
| ListMessages | GET /notify/v1/messages | 最近记录，`limit` 默认 50，最大 200 |
| GetMessage | GET /notify/v1/messages/{id} | 单条，没有则 404 |

另有 `GET /healthz`。

## 10. 配置

```yaml
notify:
  http: { addr: 0.0.0.0:2101, timeout: 5s }
  grpc: { addr: 0.0.0.0:2102, timeout: 5s }
  feishu_webhook: ""   # 留空则只走桌面
  feishu_secret: ""
  merge_window_sec: 60
  retry_max: 3
  templates: {}
```
