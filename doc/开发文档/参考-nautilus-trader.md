# NautilusTrader 功能与借鉴

| 项 | 内容 |
|----|------|
| 日期 | 2026-10-17 |
| 对象 | [nautechsystems/nautilus_trader](https://github.com/nautechsystems/nautilus_trader)，文档站 [nautilustrader.io](https://nautilustrader.io/docs/latest/concepts/overview/) |
| 核对范围 | 仓库说明、概念文档里的架构、订单、执行、实盘；Rust 工作区按 `crates/` 的职责读，不把适配器源码逐行搬过来 |
| 用途 | 按引擎功能看它怎么做，再决定本项目要补哪几条合同 |
| 许可 | 仓库标明 LGPL-3.0。只读设计，不把该运行时链进本仓库 |
| 实施 | 不新增阶段号。要补的不变量写进当前总体方案的执行合同，对应 N0、N7、N8 |

它是多资产、多场所的事件驱动交易引擎。Rust 内核跑回测和实盘，Python 只做控制面。同一套策略和执行算法代码可以进回测、沙盒和实盘。开源范围是单机回测和实盘，界面、分布式编排、内置 AI 都不在它的目标里。

本项目不换内核。Go 账本、东财文件单、A 股只做多已经定死。下面先按它的代码模块写清每个功能，再写本项目缺什么。

## 1. 代码怎么分

`crates/` 是实现。Python 包是门面。三条环境共用 `nautilus-system` 里的 `NautilusKernel`：缓存、组合、数据引擎、执行引擎、风控引擎、时钟、消息总线。

| 环境 | 时钟 | 行情 | 成交 |
|------|------|------|------|
| `backtest` | 历史数据往前推 | 目录里的历史 | 模拟场所 |
| `sandbox` | 真实时间 | 真实行情 | 模拟成交 |
| `live` | 真实时间 | 场所连接 | 模拟账户或真实账户 |

| 分组 | Crate | 做什么 |
|------|-------|--------|
| 领域 | `model` | 合约、账户、订单、持仓、行情的类型 |
| 运行时 | `common` | 缓存、消息总线、时钟、组件生命周期 |
| 行情 | `data` | 订阅、合成 K 线、订单簿 |
| 执行 | `execution` | 下单、本地模拟条件单、对账 |
| 风控 | `risk` | 提交前检查、交易状态、下单速率 |
| 账本 | `portfolio` | 现金、保证金、盈亏 |
| 策略 | `trading` | 策略和执行算法（含 TWAP） |
| 环境 | `backtest`、`live`、`system` | 回测节点、实盘节点、共用内核 |
| 场所 | `adapters/*` | 把各交易所的原始报文收成上面这套类型 |
| 分析 | `indicators`、`analysis` | 指标和绩效统计 |
| 存储 | `persistence`、`event_store` | Parquet 目录、Redis、PostgreSQL、对象存储 |

内核线程是同步的：消息分发、策略、风控、执行、缓存读写都在这一条线程上。网络和落库走别的任务，再用通道送回内核。同一进程里不能同时跑两个节点。

## 2. 逐个功能

### 2.1 消息总线

组件之间不互相持有指针。行情、命令、事件都按主题发布。策略侧是订阅；下单是点对点命令。实盘还可以把选定主题送到进程外的 Redis，那只是传输。掉电后的恢复靠缓存和事件库，不靠这条总线。

回调有优先级。优先级相同则按注册顺序，回测要能重放。

### 2.2 缓存

内存里放合约、最新行情、订单、持仓、账户。数据引擎先写入缓存，再发布。策略读到的是已经落进缓存的那一笔。可选 Redis 或 PostgreSQL 把选定状态带过进程重启。

### 2.3 数据引擎

适配器把场所报文收成统一类型，再交给数据引擎。

| 类型 | 含义 |
|------|------|
| `QuoteTick` / `TradeTick` | 报价、成交 |
| `Bar` | K 线。可由报价或成交在内部合成 |
| `OrderBookDelta` / `OrderBookDepth` | 逐笔委托变化、深度快照 |
| `Instrument` / `InstrumentStatus` / `InstrumentClose` | 合约、交易状态、收盘 |
| `MarkPriceUpdate` / `FundingRateUpdate` / `OptionGreeks` | 标记价、资金费、期权希腊值 |

K 线聚合除了秒、分、日，还有按成交笔数、成交量、成交额切的 bar，以及 Renko。信息驱动的切分只吃成交明细。

一条报价的路径：适配器解析 → 数据引擎写入缓存 → 按 `data.quotes.{场所}.{合约}` 发布 → 策略回调。订单簿走另一条更新器，不塞进这条缓存路径。

### 2.4 执行引擎与订单状态

下单默认路径：策略 → 风控 → 执行引擎 → 场所客户端。场所回报（接受、成交、拒绝、撤销、过期）回到执行引擎，改缓存，再通知策略。成交同时改持仓和组合。

订单状态分成四筐，这是它最值得抄的一块：

| 筐 | 状态 | 含义 |
|----|------|------|
| 本地尚未送出 | `INITIALIZED`、`EMULATED`、`RELEASED` | 还在本进程 |
| 在途 | `SUBMITTED`，以及「开着且在改/在撤」的 `PENDING_UPDATE`、`PENDING_CANCEL` | 已送出，场所还没给最终结果 |
| 开着 | `ACCEPTED`、`TRIGGERED`、`PARTIALLY_FILLED`，加上面两个在途里的改/撤 | 场所认了，还没完 |
| 结束 | `DENIED`、`REJECTED`、`CANCELED`、`EXPIRED`、`FILLED`、`VOIDED` | 终态 |

`PENDING_UPDATE` 和 `PENDING_CANCEL` 同时属于「开着」和「在途」。`SUBMITTED` 只属于在途。判断结束只能看是不是终态。把「不是已报」当成「已经结束」，会丢掉场所还在处理的单。

风控拒绝是 `DENIED`，单没有离开本进程。场所拒绝是 `REJECTED`。两件事不能写成同一个状态。

成交可以晚于过期或撤销到达。部分成交后过期，状态可以仍是 `EXPIRED`，但持仓要加上这笔量。凑满数量则变成 `FILLED`。过期之后又来的成交要入账，不能因为状态已经终了就丢弃。

同一笔成交重复送到，按成交标识去掉。超量成交不把仓位加过订单数量，多余部分拒绝并留下通知。场所更正成交时，原成交作废（`VOIDED`），持仓和已实现盈亏按更正重算，不能只改展示。

持仓模式：`NETTING` 一个策略下一个合约只有一条持仓；`HEDGING` 才允许用自选持仓号拆成多条。两边模式不一致时，本地可以有「虚拟持仓」，场所侧仍是一条。提交时持仓号对不上就 `DENIED`。

### 2.5 风控引擎

回测、沙盒、实盘都有同一台风控，卡在提交和改单上。撤单和查询不经过它。

不过就拒绝，并带原因码。检查包括：价格和数量的精度与上下限、名义金额、现金够不够、只减仓会不会加仓、条件单是不是已经过期、提交和改单的速率、交易状态。

交易状态越来越严：

| 状态 | 还允许 |
|------|--------|
| `ACTIVE` | 下单、改单、撤单、查询 |
| `REDUCING` | 只减仓的单，外加撤单和查询 |
| `HALTED` | 只剩撤单和查询。新单和改单都不行 |

账户选不中就拒绝，不改用另一个账户。余额和持仓只算选中的那个账户。

本地模拟的条件单有一个已知缺口：策略把单交给模拟器时，释放成市价或限价后，直接释放的那条可以不进风控检查。执行算法再提交的子单才会进风控。文档写明不能靠模拟器代替风控。

### 2.6 订单类型和时效

九种：市价、限价、止损市价、止损限价、市价转限价、触及市价、触及限价、跟踪止损市价、跟踪止损限价。场所不支持的，适配器可以在送出前拒绝，也可以等场所拒绝。

时效：`GTC`、`IOC`、`FOK`、`GTD`、`DAY`、开盘有效、收盘有效。另有只挂单、只减仓、冰山显示量。

条件关系：`OTO` 父单激活才放子单，`OCO` 一笔成交撤另一笔，`OUO` 一笔成交减少另一笔的量。括号单是入场加上止盈、止损两个子单。

场所没有的条件单，可以由 `OrderEmulator` 在本地看着行情，触发后改写成市价或限价再送出。模拟期间的单还在本地。

执行算法把一张大单拆成多张小单再送进风控。自带一种 TWAP。

### 2.7 组合与账户

账户类型：单币或多币现金、单币或多币保证金、博彩、链上钱包。组合按成交改未实现盈亏、保证金和余额。回测和实盘用同一套会计。

现金账户会看这笔名义金额是否超过可用资金。保证金账户看初始保证金。

### 2.8 时钟、标识、崩溃

系统时间是 UTC 纳秒。事件和命令用 UUID v4。价格、数量、金额在高精度构建里用 128 位定点，官方 Python 轮子默认高精度。普通 Rust 构建可用 64 位定点。比较不走二进制浮点。

不可恢复的错误在发布构建里直接中止进程，交给外部监督进程重新拉起。不在已经坏掉的进程里继续做优雅清理。重新拉起走普通启动：先从缓存和事件库恢复，再对账。场所命令不能盲目重试，这一步交给对账。正常停机仍走 `stop` / `dispose`。

### 2.9 实盘节点

启动顺序里，连接或对账失败会中止启动，策略在对账完成前不会开始。

运行中按周期核对在途单、未完成单、持仓和「自己的挂单簿」。自己的挂单簿只含本系统的单，撤单范围以此为准，不扫整个市场。

断线本身不拒绝、不撤销、不了结在途命令。证据只来自回报、查询或对账。

历史回报不完整时，可以先把订单状态对齐，但不改持仓和盈亏。持仓只有在回报集合和本地状态能证明一次连贯变化时才改。

行情队列没有自动背压，也不会自己丢数据、自己停机。队列深度、延迟上去之后，由应用决定告警、减订阅、停止新开仓或停节点。阈值是运行信号，不是延迟保证。

关闭时还有一段延迟，继续消化场所证据和本地出场计时，其间不再发起新的对账查询。

### 2.10 回测

`BacktestEngine` 或更高的 `BacktestNode` 加 Parquet 目录，按纳秒把多种历史数据灌进同一个内核。多场所、多合约、多策略可以一次跑。成交在模拟场所里发生，费用和只减仓由模拟场所执行。

文档反复写：实盘仍会多出场所、传输、计时、持久化、外部成交和对账。这些回测复现不了。策略代码相同，不表示成绩相同。

### 2.11 适配器与明确不做的产品面

适配器把 REST 或 WebSocket 收成统一领域模型。现有集成主要是加密货币交易所、外汇、境外证券和博彩，例如 Binance、Bybit、Interactive Brokers、Databento。没有东方财富文件单。

路线图写明不做：界面、分布式编排、内置机器学习、未列出的数据库和云监控。性能上它可以用来喂强化学习，那不是一套交易策略。

## 3. 本项目已经有的，不必再立项

| 它的做法 | 本项目 |
|----------|--------|
| 回测和交易共用规则与会计 | `pkg/rules` 与模拟撮合；日线信号下一交易日成交 |
| 提交前风控，拒绝则不到场所 | R00–R15，`CheckOrder` 超时按拒绝 |
| 急停后限制新开仓 | Kill Switch 持久化，停买，人工卖出仍可走 |
| 未完成单不换号重下 | `UNKNOWN` 只查原单；文件单要有稳定单号 |
| 写出文件不等于场所接受 | 总体方案已写：CSV 接受只是文件状态 |
| 断线、账户过期、对账差异停止新开仓 | N 序列的失败处理 |
| 启动后先对账再恢复授权 | N7、N8 |
| 只做多、净额一条持仓 | T+1，一票一条多头。不需要 `HEDGING` |
| 条件单不挂进终端 | 止损止盈由盯盘生成普通限价文件单 |

## 4. 需要补进合同的功能

这些是它的代码里有、本项目的状态机或失败处理还没写成硬规则的部分。都落在现有 Go 账本上，不引入该引擎。

| 编号 | 要增加的行为 | 原因 | 落到 |
|------|----------------|------|------|
| E1 | 订单分四筐：本地、在途、开着、结束。结束只看终态。提交中和撤单中都算在途 | 「不是已报」会被误当成已结束，场所还在处理 | M09 状态机，N7 |
| E2 | 风控拒绝和场所拒绝分成两个终态 | 现在「柜台拒绝」和提交前拒绝容易混在同一条结束线上 | M09，N7 |
| E3 | 撤销或过期之后到达的成交仍改持仓和现金。凑满数量则改为全部成交 | 文件回报会晚到 | M09 对账，N8 |
| E4 | 成交以场所回报里的成交号去重。超过订单剩余量的部分入账失败并告警，不加进持仓 | 回报重放和超量成交 | N7、N8 |
| E5 | 预留「成交作废」：权威更正要回滚该笔持仓和已实现盈亏，不能只改界面 | 柜台更正回报 | M09，可在 N8 联调时做，状态名先留 |
| E6 | 盯盘触发的止损、止盈在写成文件单之前再过一次最终风控 | 它的本地模拟器释放订单时可以绕过风控。这里不能学这个缺口 | M08 与 trade，N7 |
| E7 | 同一持仓的止损和止盈互斥。一笔已经写出或成交，另一笔必须撤掉或不再写 | 它的 `OCO`。终端里不挂两套条件，本地仍可能连写两张卖单 | M08、M09，N7 |
| E8 | 终端里人工下的单记为外部成交，带来源。对账差异停止新开仓，不自动改平 | 实盘节点把场所上的外部活动当证据 | N8 |
| E9 | 行情断流、扫单目录超时、进程重启，都不把在途单标成拒绝或已撤 | 断线不是命令结果 | N7、N8 |
| E10 | 进程中止后由外部重新拉起。拉起后的第一件事是对账。对账完成前不产生新的买单 | 崩溃进程里继续清理会把坏状态写出去 | N7 |
| E11 | 行情或执行队列持续超阈值时停止新开仓，不丢弃行情来追平 | 它的队列没有自动丢数，停不停由应用决定 | 监控与 N7 |
| E12 | 停牌、临停、集合竞价未结束，是提交前的拒绝原因，界面写明状态 | `InstrumentStatus`。没有行情和不能交易不是同一句 | M02、风控，N4 之后接到 N7 |
| E13 | 比较和撮合用「分」和「股」的整数。展示再格式化 | 它用定点。A 股不需要 128 位，但不能用浮点判断价格是否成交 | `pkg/rules`、模拟撮合 |
| E14 | 当日有效的单到收盘未完成则变为过期终态，不留在在途 | `DAY`。A 股不做 `GTC` | M09，N7 |

Kill Switch 不要改成它的 `HALTED`。它的 `HALTED` 连新的卖单都不许。本项目停的是新开仓，人工卖出和已授权的盯盘卖出仍要能过风控后发出。

## 5. 明确不搬

| 它的功能 | 本项目 |
|----------|--------|
| 换用该 Rust 内核或 PyO3 绑定 | 第二套账本。LGPL-3.0 也不并进本仓库 |
| 加密货币、外汇、期权、保证金、博彩适配器 | 东财文件单，只做多 |
| 纳秒时钟、128 位价格、订单簿做市、TWAP 拆单 | 超短用分钟和日线，整手限价 |
| `HEDGING` 多条持仓、只减仓加杠杆 | 一票一条多头 |
| Parquet 行情目录替换 PostgreSQL | 事实仍在现有库 |
| 用它的指标库和绩效库替换 M02、M07 | 口径已经在本项目 |
| 强化学习训练环 | 模型只打分。回测不重放大模型 |
| 本地条件单触发后跳过风控 | E6 要堵上这条 |

## 6. 和现有阶段的关系

不单开 P 或 N 编号。E1–E11、E14 写进 N7 的订单和恢复验收。E3、E5、E8 在 N8 用文件回报对上。E12 的状态字段在行情侧出现后，风控才能引用。E13 跟模拟撮合的下一次正确性修改一起做，不单独立项换数据库类型。
