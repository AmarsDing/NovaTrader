## N2-02 trace端口（2026-10-18）

生成合同GetTrace经Gate认证，`GET /api/ops/traces`→AuditStore→outbox白名单投影。精确trace过滤，最多200条，pending/leased/retry/dead/published分别表达；无业务消费者ACK推断。研究任务与条件计划写操作仍受owner+请求审计保护，转发前审计不代表下游执行成功。见[事件记录](../实施记录/N2-02-事件租约与追踪-2026-10-18.md)与[集成记录](../实施记录/N3-02-03-监控与盯盘集成-2026-10-18.md)。

## N2-01 环境观测补充（2026-10-18）

EnvironmentObservability生成绑定注册到Gate，鉴权后固定配置地址/internal/observability探测：3并发、700ms单探针、3秒整轮、128KiB响应，禁止重定向/请求选址/凭据地址，5秒缓存合并窗口请求。固定操作合同校验；仅回安全分类，保留源时间，超10秒偏差标unknown，不冒充时钟已校准或业务ready。详见[实施记录](../实施记录/N2-01-消费者与环境观测-2026-10-18.md)。

版本 v0.3。

保留现有 Kratos 启动、中间件、WebSocket 和 NATS 封装。删除机场、NTP、SNMP、资产、告警中心等模板接口，以及 `data.go` 里对不存在包的引用。

敏感操作：实盘开关、Kill Switch 复位、风控参数、策略版本批准。这些接口要求 Owner，并写 `audit_log`。

桌面只访问 admin。`POST /api/v1/login` 签发 7 天令牌，角色是 `owner` 或 `viewer`。账号在 `configs/config.yaml` 的 `admin.users`，密码存 bcrypt。除登录外，`/api/*` 都要 `Authorization: Bearer`。Viewer 不能写。

页面数据不在网关里重算，按路径转到对应服务：`/api/market` → 2021 `/v1/market`，`/api/intel` 和 `/api/kb` → 2031，`/api/risk` → 2081 `/risk/v1`，`/api/trade` → 2091 `/v1/trade`，`/api/strategy` → 2061，`/api/backtest` → 2071，`/api/brain` → 2051，`/api/notify` → 2101 `/notify/v1`，`/api/datahub` → 2011 `/v1/datahub`。请求头 `X-User` 改写成登录名。

`GET /api/ops/status` 返回 `services`、`sources`、`models`、`resources`。数据源来自 datahub，模型档来自 brain 的统计接口。`resources` 是本机磁盘（进程所在盘，剩余不足 10% 标 down）和 `nvidia-smi` 读到的显存；没有显卡驱动时显存一行状态为 down，不编造数字。

## 网关入口观测 v1（2026-10-15）

合同源为`api/admin/v1/observability.proto`，生成HTTP/Go绑定后注册到原Gate，Hub提供只读快照。scope固定`admin_gateway_ingress`；在报价合并前记录接收/接纳/字节/错误。60个一秒桶，返回起止/实际观测秒/完整性/进程启动时间；当前秒是部分桶。最多128计数组、80条最近样例，溢出聚合与截断显式说明。重投可能重复计数，不能当业务ACK或唯一订单数。

路由登记保留subject/topic/durable/transport，bindingState由实际订阅建立结果更新为declared/bound/failed，并带更新时间；natsConnected独立。subject精确过滤，trace_id仅过滤样例，统计口径不因trace筛选而误写。固定白名单投影后下发，禁止返回账户资金/持仓和原文；source_time未知不使用event_time或gateway_received_at替代。前端节点/边只关联主题，不把入口计数当每条内部结构边的实测流量。详细合同、验证与未实现指标见[首批集成](../实施记录/首批集成-2026-10-15.md)。

## 可恢复 WebSocket 协议 v2（2026-10-15）

数据流：NATS Envelope→`Hub.onRaw`→保留payload与完整metadata→按主题500帧环→订阅确认/恢复水位→桌面async消费者→已完成序号。接口仍是`2003/ws?token=...`，不引入第二条消息总线。

订阅整体替换：

```json
{"op":"sub","topics":["signal","position","alert"],"server_epoch":"admin-instance-uuid","request_id":2,"resume":{"signal":1203,"position":80,"alert":20}}
```

初次实例、复制会话到新窗口以及显式缺口用`op=resync`强制读取基线。存储cursor不是持久化实体状态；新窗口即使继承sessionStorage也必须恢复自己的store。切后端不继承其他endpoint游标；stop/logout清空游标并取消旧请求。

服务端先确认各主题边界：

```json
{"topic":"sub_ack","server_epoch":"admin-instance-uuid","request_id":2,"data":{"topics":{"signal":{"head":1206,"oldest":707,"after":1203,"status":"resumed"}}}}
```

`oldest=head+1`表示尚无缓冲帧。无epoch、不同epoch、未给该主题cursor、after大于head/为负、after小于oldest-1都不能直接补推。返回`status=resync_required`以及独立`topic=resync_required`控制帧，reason分别标识`epoch_required/epoch_changed/snapshot_required/cursor_ahead/replay_expired/client_resync`。不同主题可分别恢复，原生WS按连接有序，request_id防迟到ACK改变新订阅。

恢复时冻结该主题head为水位W，暂停向该连接直接投递该主题，事件继续进入同一环。前端`onResync(topics, async handler)`声明能恢复哪些主题，handler必须等待权威REST查询和有效性校验，失败throw。没有handler保持required。处理器完成后客户端发：

```json
{"op":"resync_ack","server_epoch":"admin-instance-uuid","request_id":2,"resume":{"signal":1206}}
```

服务端在同一锁内验证W和环窗口，先发resync_ack（含after=W和当前head），再回放seq>W，之后放行live。同一锁也序列化普通订阅ACK/回放/live，避免交接窗口漏帧/乱序。回放每25帧组成`replay_batch.data.frames`，最多500帧不会直接塞满transport的100消息队列。若REST期间超过500帧，再发`recovery_window_expired`与新的水位，不回放不完整后缀，不伪称已恢复。

业务帧（`seq`仍保留为旧别名）：

```json
{"topic":"signal","e":"signal","server_epoch":"admin-instance-uuid","topic_seq":1207,"seq":1207,"data":{"signal_id":"s1","stock_code":"600000"},"metadata":{"schema_version":1,"event_id":"evt-id","trace_id":"trace-id","subject":"strategy.signal.updated","source":"strategy","time":"2026-10-15T01:30:00Z","gateway_received_at":"2026-10-15T01:30:00.008Z"}}
```

metadata为原Envelope去掉payload，旧e/d与data仍保留；原始time及可选source_time/received_at/published_at不被网关时间覆盖。没有源时刻就保持缺失。非法新版本由events.Unmarshal拒绝，不伪造证券身份。

前端同主题串行等待返回Promise的onPush消费者，成功后才保存seq，重复/旧帧丢弃；非连续新帧请求resync。同步期间数据缓冲上限1000，超限重新握手；消费积压上限1000则断连重试。处理失败不推进cursor。动态增退订/重连/登出取消旧AbortSignal与旧request_id，迟到恢复不能ACK新epoch。replay帧带`replayed=true`交给read model，历史LIVE确认/桌面通知不重新触发。不能借回放授权交易。

**一致性边界**：当前REST查询分属各服务，未提供统一数据库LSN/实体snapshot version；W是网关事件边界，不是REST事务水位。恢复handler先读权威状态，回放作为刷新失效通知再次权威读取，不能把旧payload直接覆盖REST新值。只有返回Promise的消费者受提交等待保障，旧void/fire-and-forget监听不因此获得原子一致性。`link.sync=ready/isLive`表示声明恢复和WS连续交接完成，不代表NATS、数据源、账户对账或全部页面业务ready。N1-02按各store的readiness和版本合同继续验收。

行情每秒flush一次按key缓存：允许的可替换报价/因子/批次状态按事件类型+证券+频率，bar再加时间桶；没有时间桶的bar、异动/涨跌停变化与未知事件直接进入环。批次market.snapshot按来源单独合并，没有证券不能编symbol。每秒可能产生多个key的帧，不能仍写成整个market主题每秒最多一帧。关键订单/成交/风险不合并；transport队列满关闭慢端，留在环里的事件可续传，超窗靠权威查询恢复状态。审计与成交历史持久性属于领域账本，不由WS环承担。

`GET /api/ops/nats`增加ws.server_epoch/replay_capacity/slow_disconnects/resyncs。durable消费积压用过滤消费者`NumPending`，lag保留兼容字段但basis固定为`filtered_consumer_num_pending`；独立展示NumAckPending/NumRedelivered，不能用全流LastSeq减过滤消费者Delivered.Stream冒充lag。未接入最老积压年龄与P95时延，不编数字。

`POST /api/ops/backup` 触发一次数据库备份（FR-11-08 的备份半）。要求 Owner，且请求体 `{"confirm":"BACKUP"}` 作二次确认；缺口令 400，非 Owner 403，未接 runner 503。实现走 pg_dump 逻辑备份：输出目录 `NT_BACKUP_DIR`（默认 `backups/`），可执行文件 `NT_PG_DUMP`（默认 PATH 里找）；数据库密码只进子进程环境（PGPASSWORD），不落命令行和日志；失败删掉半成品文件，stderr 截断 300 字符后随错误返回（密码脱敏）。成功/失败都写 `audit_log`（action=ops.backup，记入敏感动作）。前端 OpsView 是口令输入墙 + 结果行；pg_dump 可能跑几分钟，请求超时放宽到 10 分钟。这是冷备份；PITR/归档属部署层，不在网关范围。

FR-11-08 的服务重启半不做：admin 重启不了同级进程，需要外部进程管理器，当前部署没有；重启在机器上手动执行。
