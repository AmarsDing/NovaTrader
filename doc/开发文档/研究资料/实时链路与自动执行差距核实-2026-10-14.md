# 实时链路与自动执行差距核实

核实日期：2026-10-14。范围：当前工作区手写代码，包含本日尚未提交的修正；未把生成代码、设计中的接口或已有完成百分比当作运行证据。本文不修改业务代码，也不表示已跑通交易日端到端联调。

结论：现有 Go 服务、Redis 快照、NATS/JetStream、outbox、规则/模型分层及 Vue/Tauri 画布具备继续建设的基础。优先事项是修复真实跨服务合同、建立可测的时效和恢复机制，再补逐边观测与自动执行。更换渲染风格或新增预测模型不能直接解决这些缺口。

审计开始时，用户所说 **JEV 模型** 的精确身份尚未确认；后续已核实指 **TypeSafe AI 的 Jev（System One 结构化判断模型）**。官方文档确认它接收文本状态并返回限定类型的判断，见[System One](https://docs.typesafe.ai/concepts/system-one)。本文保留这一核实过程，原代码差距结论不受影响；Jev 与仓库已有的 JetStream 消息基础设施分开，也不等同于 JVM 或 JEPA。

## 2. 必须先修复的真实合同

### 2.1 账户事件无法被风控按设计消费

`trade.Engine.Snapshot` 在 `backend/app/trade/internal/biz/engine.go:430` 先写快照，随后 `:433` 用 `Payload: view` 发 `trade.account`。`AccountView` 在 `internal/biz/types.go:62` 无 JSON 字段标签，字段为 `Book/Cash/Equity/...`，且缺少持仓、在途委托、日初权益、源时间和账户代际。

风控 `AccountPayload` 在 `backend/app/risk/internal/biz/payload.go:12` 需要 `account_type/available/day_start_equity/holdings/open_orders/as_of`。`OnAccount` 在 `engine.go:371` 明确拒绝非 `SIM/LIVE` 的 `AccountType`。因此 JSON 成功解码并不表示账本成功更新。另有对账事件复用 `trade.account` 且载荷仅 `book/halted/diffs`（trade `engine.go:540`），需要与完整快照分成不同类型。

先定义唯一领域事件 `AccountSnapshotV1`：`account_id/book/as_of/source/generation/equity/cash_available/day_start_equity/holdings/open_orders/quote_basis/reconciliation_state`，写快照和 outbox 同一事务。风控启动时读最新完整快照，再接事件；消费者验证版本、账户、时间、代际，拒绝乱序和半份快照。

验收：用真实 trade 生产函数输出的 JSON 驱动真实 risk 解码，验证现金、T+1 可卖、在途冻结、日亏基准与 SIM/LIVE 隔离；账户断流、逆序、缺字段、对账事件都不能把账户改成空仓或可用。

### 2.2 WS 续传不能穿越 admin 重启

- 后端 `hub.go:211` 自增进程内 seq；每主题缓冲 500 帧；`:184` 只回放大于 resume 的本进程帧。
- 前端 `web/src/ws/hub.ts:44` 开始维护 seq，在 sessionStorage 保存；`:154` 对 `n <= seq[topic]` 丢帧。
- 推定的可复现故障：前端记住 seq=1000，admin 重启后从 1 计数；后端不会回放更小的序号，前端也会丢弃新 1…1000。REST 可以另行取到当前值，但不修复这段推送断层。

定义 `server_epoch/topic_seq/head_seq/oldest_seq`，订阅响应返回 `resync_required`。epoch 变化、客户端序号超前、缓存覆盖或中间 gap 时执行“获取最新快照及水位→应用后续增量”。关键交易状态从业务查询恢复，不能要求前端重放通知来重建账本。为增量回放加总量上限和确认水位，防止连接恢复时洪泛。

验收：seq=1000 后重启，3 秒内得到新 epoch 并恢复后续事件；断开超过 500 帧明确快照补齐；重复/乱序帧不重复套用；多窗口订阅与退出不丢当前状态。

### 2.3 信封到前端丢失，部分脉冲解析不匹配

`events.Envelope` 已有 `event_id/trace_id/time/source/subject`（`backend/pkg/events/envelope.go:83`），但 admin `hub.go:337` 解包后只传 `env.Payload`，因此不能基于该 WS 帧建立可靠的跨服务因果追踪。

监控 `web/src/monitor/pulses.ts:15` 仅取信号 `id/symbol`，实际 `SignalUpdated` 用 `signal_id/stock_code`（`backend/app/strategy/internal/biz/signal.go:125`）；`:20` 的行情脉冲要求 `symbol`，真实 `market.snapshot` 是批次元信息，不包含单证券 symbol。应该区分“批次写入事件”和“证券报价事件”，按真实载荷归一化；没有标的就显示批次/源，而非编造一只股票或脉冲。

事件外壳追加兼容 `schema_version/causation_id/correlation_id/source_time/received_at/entity_id/entity_version`；WS 保留这些字段，payload 保持原业务结构。`trace_id` 表示因果链，`event_id` 表示具体事件，不能混用。画布“结构依赖”和“有真实事件的路径”使用不同标记。

验收：从采集批次、候选、研判、信号、风险决定、订单到成交的一个人工样例可以沿 ID 查到真实记录；没有真实事件的边仍显示“未观测”。

### 2.4 信号到订单仍缺执行编排

trade runner 当前订阅 `market.bar.1m` 和 `risk.exit`（`backend/app/trade/internal/core/runner.go:42`、`:48`）；并未订阅 `strategy.signal.updated`。风险请求 `CheckIn`（`biz/biz.go:42`）及 `RiskClient.Check`（`data/risk.go:33`）也未传信号/策略版本/持仓代际/授权证明。

新增后端执行编排器，流程为：批准且有效的信号→读取账户/行情/参数版本→条件触发→持久化执行意图并固定唯一订单 ID→必要人工确认→提交前复检最新账户/行情/计划/授权并执行最终风控→同 ID 提交→回报→信号状态回写。确认期间的预检结果不能当作提交时许可。前端重查用于体验和防误操作，后端仍须独立重查。

验收：一个信号并发 100 次只创建一个可提交意图；已过期、撤销、错账本、价格不符、策略版本变更、持仓代际改变时拒绝；自动流程不依赖某个桌面窗口持续打开。

## 4. 快链路、慢链路与时间测量合同

原则：**规则与风控快速响应，研究与长文本异步完成。** 当前 3 秒采集节奏不支持宣称毫秒级源行情交易，更不是高频交易。先采样测量后调阈值，目标与实测分栏。

### 4.1 每个时刻的含义

| 时间字段 | 产生位置 | 用途 |
|---|---|---|
| `source_time` | 数据源，保留原时区/精度/已知程度 | 报价/新闻真实发生与首次可用时间；未知保持未知 |
| `received_at` | 首个自有接入进程 | 外部采集延迟；HTTP 成功不是源时间 |
| `normalized_at` | datahub 质检结束 | 转换、校验耗时和拒绝比例 |
| `cache_written_at` / `db_committed_at` | Redis/PG 写成功后 | 消费者真正可读的水位；不能在调用前填写 |
| `enqueued_at` / `started_at` / `finished_at` | 排队/推理/规则 worker | 排队与执行耗时分开，缓存命中单独计 |
| `published_at` / `consumed_at` / `acked_at` | outbox/消息消费者 | 投递、业务完成、确认的不同语义 |
| `pushed_at` / `client_received_at` / `rendered_at` | 网关/桌面 | WS 等待、浏览器处理和可见呈现延迟 |

字段统一 UTC 保存、上海时区显示。持续时长优先使用本进程单调时钟；跨主机绝对时刻只有在时钟偏差受监测时用于精确延迟，否则展示估计及不确定性。源时间未知时只统计“自有接入到屏幕”，绝不伪称源到屏幕。quote age、news age、signal validity、account age 分别显示，禁止一个全局 `sampledAt` 给所有数据保鲜。

### 4.2 第一阶段候选 SLO（待基线后定稿）

| 链路 | 初始目标 | 测量/降级 |
|---|---|---|
| 自有行情接收→Redis 可读 | P95 ≤ 300ms，P99 ≤ 1s | 不含外源轮询等待；失败保留旧价且过期不可下单 |
| 有已知源时间的快照→Redis | 沿用 M01 P95 ≤ 3s 的需求，先测是否当前 3s 轮询能达到 | 必须按源/时段/证券覆盖显示；若源节奏更慢，标能力不支持，而非改时间戳 |
| Redis 批次→规则因子/行情状态 | P95 ≤ 500ms | 增量计算；按证券数、批次大小、CPU 负载记录 |
| 内部风险/订单状态提交→桌面可见 | P95 ≤ 1s，P99 ≤ 2s | 关键消息优先级，无法满足时显示延迟并禁止误判已完成 |
| 入站 WS→可见更新 | P95 ≤ 100ms；持续 30FPS 基线 | 业务 store 合并、增量渲染；视觉动画可减频，关键状态不等动画 |
| 最终风险规则计算 | 计算 P99 ≤ 50ms；HTTP 端到端另列 | 现有 RiskClient 200ms timeout 是超时边界，不是已测性能；超时拒单 |
| 规则候选条件触发→形成执行意图 | P95 ≤ 1s（自有有效快照起算） | 不等待长文本模型；最终执行仍受时段、行情、账户和风险限制 |
| AI 研究/研判 | 按任务/model 单独测队列、推理、token、P95 与超时 | 当前 AnalyzeTimeout 默认 30s；先给“研判中/降级”，长任务不阻塞风控 |
| 环境指标 | 关键服务/连接 1–2s；主机资源 2–5s；重型 DB/GPU 查询 10–30s | 统一采样器缓存结果，UI 订阅，不让每窗口触发重型探测 |

以上目标均为拟议验收，不是当前性能报告。每项必须附环境（Windows/DGX、CPU/GPU、源、证券数、订阅窗口数）、样本量、失败率、P50/P95/P99、统计窗口及“未知/不适用”状态。

| WS | `hub.ts:143` 附近同步逐 listener 分发；健康检查 5 秒；seq 每帧写 sessionStorage | 潜在主线程压力来源，但未做 10k msg/s 浏览器性能测试，不称为已发生 JS storm |

优化顺序：协议 epoch/gap→共享 typed store 的 snapshot+delta→每业务域 single-flight/invalidation 合并→可见面板按需订阅→前端渲染频率分层。行情按 symbol 最新值合并，订单按 order_id 的状态版本应用；不能用“只保留最后一条”吞掉独立订单/告警。

接受标准：录制或合成可控输入 5000 证券、20–50 个可见节点、1/3/8 个面板、正常及 10 倍突发；跟踪每秒请求数、WS 入站/合并/丢弃/重同步、长任务、帧率、内存、订阅数。连跑 30 分钟无持续内存增长；关键风险与订单不丢，背景时资源下降，恢复后水位一致。具体消息负载按真实采集能力设置，10k msg/s 可做极限试验但不作为当前源能力的宣传。

## 6. 监控应展示什么真实内容

保留现有原监控画布、HUD、终端带和盯盘票式结构。画布每个节点增加“业务就绪/连接/数据可用/数据年龄/运行负载/权限”分开的状态，防止把进程活着涂成业务健康。

- **环境**：主机 CPU/内存/磁盘/网络/时钟偏差，Go 进程 goroutine/GC/堆，Python worker 状态，GPU 利用/显存/温度/队列，PG/Redis/NATS 实际连接与容量。按 Windows 交易机、DGX、本地桌面分组，采样进程自身与宿主机口径分开。
- **数据**：预期/已收/新鲜/拒收证券数、源 age 分布、补数、源切换、配额、错误样本、引用版本；消息情报显示发布/首次接收时间、重复合并、来源和证据关系。
- **流**：节点接收/处理/拒绝/发布速率，边的真实 subject、消费者名、schema 版本、P95、pending/ack_pending、最老等待年龄、重投、死信、最近样例 ID。高基数 trace/symbol 不放 Prometheus 标签，进入结构化事件/日志索引。
- **执行**：意图数、风控通过/缩量/拒绝、待确认/待提交/UNKNOWN/在途/成交、对账差异、保护规则覆盖与最后执行时间；SIM/LIVE 及授权级别始终可见。
- **配置**：读取值、保存版本、服务已加载版本、生效范围、校验、影响预览、冲突、回滚；保存成功不等于所有服务生效。

“整个环境”先限定为已登记的服务/主机/边车/基础设施。登记表标明观测覆盖和未接入项；缺指标不能补 0，不能用动画表示已测传输。

## 8. Jev：新闻相关性、证据分类与任务路由影子实验

### 8.1 已核实的产品能力与边界

Jev 是 TypeSafe AI 的 System One 模型，当前只支持文本输入，包括字符串和结构化对象/数组里的文本，不直接接收图片、音频、视频；它输出结构化判断，不生成推理说明长文。官方说明群体层面的概率校准不保证某次判断正确，见[System One](https://docs.typesafe.ai/concepts/system-one)。

调用形式为 `state + questions → answers`，可通过 SDK 或 `POST https://api.typesafe.ai/v1/systemone` 使用，示例模型别名是 `jev-latest`。本次核实的是需要 API key 的托管接口；这些资料不能作为“已开源模型权重、可在 DGX 本地部署”的证据，开源 SDK/skill 也不等于权重开源。见[Quick start](https://docs.typesafe.ai/introduction/quickstart)及[API reference](https://docs.typesafe.ai/api)。

| 原语 | 官方含义 | NovaTrader 拟议影子任务 |
|---|---|---|
| `Choice` | 从指定选项选择，返回选项及概率分布 | 新闻/公告/传闻/重复/待复核；路由到个股消息、行业、外围或人工复核队列 |
| `Score` | 按定义的有序等级打分，返回概率加权分值 | 按统一量表评估“与当前标的相关程度”或“该文本对证据条目的支持程度” |
| `Noul` | 判断给定陈述是否为真，返回“是”的概率 0–1 | 文本是否明确提及该公司；是否存在与当前事实包相冲突的陈述；是否需要升级复核 |

三个原语的配置及返回字段以[API reference](https://docs.typesafe.ai/api)为准。Jev 判断的是所定义的文本问题：相关性分数、证据分类或 `Noul` 值均不等于股价上涨概率、买点成功率、收益保证，也不构成来源真实可靠的证明。

### 8.2 接入位置与失败语义

先在 M03 情报处理的旁路实现可关闭适配器，保留现有规则/四维模型流程。输入使用公开新闻摘要、来源标识、发布/首次接收时间、候选证券名称及明确的问题量表；账户凭据、资金/订单明细不进入该托管请求。结构化输入属于文本状态，不把原生 K 线图或用户视频直接送入接口。

返回结果追加到影子判断记录：`input_digest/news_id/symbol/question_schema/model_requested/model_returned/answer/distribution/confidence/latency/received_at/expires_at/status`。保留实际返回版本，不能仅记会滚动的 `jev-latest`；来源和证据编号由系统校验绑定，模型结果不新增虚构证据。

实验任务只比较“新闻相关性/证据类别/任务路由”的质量与耗时。价格、仓位、时段、T+1、涨跌停、账户有效性、Kill Switch、最终风控仍是本地确定性规则。**风控与持仓保护快链路不等待 Jev**；超时、限流、服务不可达或低置信时回退到规则/当前模型或待复核，不把未知结果记为利好/无风险。

### 8.3 从影子到辅助路由的验收

1. 建立中文金融文本人工标注集，分公司/板块/事件/时间留出测试，验证消歧、标题党、传闻、重复转载、否定句、过时消息和提示注入。目标是文本任务，不用事后涨跌给新闻真实性打标签。
2. 与现有规则、当前小模型比较分类精确率/召回率、误丢重大负面率、人工复核量、覆盖率和分组校准；财务/监管等必须处理的事件保留确定性优先通道，不能被普通路由分数静默过滤。
3. 测量中国交易环境到托管服务的网络、排队、推理、总 P50/P95/P99、超时/失败率、成本及限流，使用脱敏历史样本或模拟服务完成故障测试。官方“快判断”描述不等于项目已测实时能力。
4. 影子期间只记录差异，不驱动下单或替换风险结论；达到预先冻结的质量/成本/时延阈值后，才小范围用于辅助路由，并保留一键回退、版本固定与持续漂移评估。

后续股票走势预测属于独立的时间序列/因子研究任务，需要防未来函数、样本外检验、交易成本和可成交性验证；不能因接入 Jev 文本结构化判断而宣称已经实现。
